(A) DO THE NUMERIC COLUMNS ALIGN WHEN READ STRAIGHT DOWN?

  MODEL LIST — YES. Measured mechanically from the width-140/30d render above:
  every one of the 8 model rows ends at exactly column 136. The figures are
  right-aligned to a shared end column, which is why '$90.73' and '$0 · 210 req'
  both finish in the same place despite very different lengths.

  STAT STRIP — YES, but on a DIFFERENT and correct rule. The strip is a grid of
  EQUAL-WIDTH COLUMNS, so each figure sits at the same offset inside its column
  and consecutive figures are spaced by exactly one column plus one gutter.
  At width 140 that reads:
      requests    65,460    cost        $112.36   error rate  2.01%     cache share 95.9%
  — even intervals, which is the property the eye uses.

  What is deliberately NOT claimed: the four figures do NOT share one absolute
  column, and cannot. Cell i begins at i x (column + gutter), so only the row's
  LAST cell reaches the right edge. Right-aligning every figure to a single
  absolute column is possible only for a row holding ONE cell, which is the model
  list's shape and not a strip's. An earlier version of this screen joined whole
  cells with three spaces and let them fall where they fell, which put the figures
  at columns 11, 27, 51 and 73 — no two comparable. That is fixed and tested.

   cache-read — a single combined total would be a number describing nothing.

   (e) THE TREND IS AN ESTIMATE AND SAYS SO. /api/stats/model-dashboard returns
   per-model REQUEST counts only; the per-model COST series (CostTimeSeriesPoint)
   lives behind /api/stats/costs, which this screen does not declare because
   `needs` is owned by the registry in types.ts. So each trend is
   `daily requests x this model's measured average cost per request`, printed with an
   `est.` prefix and footnoted on the screen itself. A model whose spend grew
   because it served more requests draws a different shape than one whose price
   per request rose, and only a reader who knows it is an estimate can read that
   difference. When the average cannot be formed — no requests, or $0 with
   unpriced requests outstanding — the trend is OMITTED rather than guessed.

   (f) ALL-ZERO TRENDS SIT ON THE BASELINE, NOT AT FULL SCALE. At 24h every
   model has a real all-zero price card, so every cost is genuinely flat at
   zero. Each prints a run of '▁' plus 'flat at $0/day' — rule 2 of renderSparkline. Dividing by
   a guard value of 1 would have painted every one of those as a FULL bar,
   which is the failure mode that guard exists to prevent.

   (g) THE 24h CAPTURE SHOWS NO BARS WORTH THE NAME, AND SAYS WHY. At 24h the
   top model costs $0 across 4,068 requests, so the ranking is decided by
   request count rather than money, and the bars are all one cell. That is
   the truthful reading of a free-tier day, not a broken chart: the "$0" is a
   real price from a zero-price catalog card, which is why it prints "$0 ·
   4,068 req" rather than a bare "$0".
